## What this is

Origin fraud in protected-designation food isn't forged certificates — it's volume. Bronte produces ~3,400 tonnes of PDO pistachio per harvest, biennially, yet "Bronte pistachio" sells worldwide year-round. Attestation can't catch this: you can always issue one more certificate.

QUOTA replaces attestation with a conservation law. A consortium mints exactly one origin unit (= 1 gram) per certified gram at harvest. Units move down the supply chain under transfer restrictions. Processing retires input units and mints derived units capped by a declared yield ratio. Units are retired at retail. Supply can never exceed the harvest, at any stage.

## Core invariants (protect these)

```
minted(season)  <= cap(season)              [grams]
retired         <= minted
derived_grams   <= input_grams * yield_bp / 10000     [always floored]
cap is set once at season open, never raised
retiring does NOT free headroom to mint again
```

All ratio maths uses integer basis points and always rounds down (floor division). Rounding up would create units from nothing.

## Unit discipline (non-negotiable)

The atomic unit is one GRAM. Every integer in contracts, scripts, subgraph and relayer is a count of grams. Never name a variable `*Kg` — use `*Grams` everywhere. Convert to kg only at the UI rendering edge. HTS `decimals` affects display only — `maxSupply` and every mint/transfer amount is expressed in grams.

## Design decisions

### Retire, don't burn

Hedera HTS `maxSupply` on a `FINITE` token caps **circulating** `totalSupply` — mint increases it, burn decreases it, same semantics as ERC-20 `totalSupply`. A literal burn lets minting resume afterward, which destroys "supply can never exceed the harvest."

Confirmed empirically against the live token (`0.0.10411251`), not assumed:
```
Total supply before burn:  3,400,000,000 grams (at cap)
Burn 100,000 grams:         status SUCCESS
Total supply after burn:   3,399,900,000 grams
Mint 1 gram:                 status SUCCESS
Total supply after mint:   3,399,900,001 grams
```
Burning did reopen mint headroom.

Fix: **the product never calls `TokenBurnTransaction`.**

- Consumption at retail / processing input consumption = transfer units to a dedicated **retirement account**, made permanently unable to send anything back out (see Making retirement permanent, below, for how). Circulating `totalSupply` never decreases, so `maxSupply` is a true **lifetime issuance cap** enforced by Hedera consensus — the "cap enforced by consensus, not our code" claim holds.
- The retirement account's balance (readable from the mirror node) is the public "consumed" figure.
- This mirrors how carbon credits and renewable Guarantees of Origin are actually retired.
- Transformation: input units are **retired**, not burned. Derived units are minted on a **separate token** whose `maxSupply` = `input_cap * yield_bp / 10000`, floored.
- Built and verified against the live token — see Status.

For reference, minting past the cap in the first place is rejected outright:
```
Mint 1 gram beyond cap (total supply already at maxSupply): status TOKEN_MAX_SUPPLY_REACHED
```

### Making retirement permanent

**Security property, stated precisely:** the retirement account's key is not secret — it's deterministically derived from a published formula, so it provides no cryptographic protection. Retirement here means *any reversal is publicly visible and attributable to a specific known account*, not *reversal is physically impossible*. That distinction matters and should never be blurred in the README or pitch.

Four things tested against the live token (`0.0.10411251`), in order — status codes measured, not assumed:

1. **Unsignable account at creation (empty KeyList, or impossible threshold key) — rejected by Hedera itself.** `hedera/investigate-unspendable-key.mjs`.
   ```
   AccountCreateTransaction, key = empty KeyList (0 members):              KEY_REQUIRED
   AccountCreateTransaction, key = KeyList(1 member), threshold 2 (2-of-1): INVALID_ADMIN_KEY
   ```

2. **Same two constructions via `AccountUpdateTransaction`, rekeying an already-associated account — also rejected.** `hedera/investigate-post-association-unspendable.mjs`. Tested specifically because option 1's constraint might only apply at creation, not update.
   ```
   AccountUpdateTransaction, new key = empty KeyList:              INVALID_ADMIN_KEY
   AccountUpdateTransaction, new key = 2-of-1 impossible threshold: INVALID_ADMIN_KEY
   ```
   Hedera enforces key satisfiability everywhere a key can be set. **There is no Hedera mechanism, at creation or after, for a genuinely unspendable account.** This is a protocol wall, not a workaround we missed — settle this permanently, don't re-investigate it in a future session.

3. **Freeze with the token's `freezeKey` — works, rejected on design grounds.** `hedera/create-retirement-account.mjs` + `hedera/freeze-retirement-account.mjs` + `hedera/prove-retirement-immutable.mjs` (kept as a proven-but-superseded prototype; account `0.0.10421765`, 50,000 grams, frozen, `ACCOUNT_FROZEN_FOR_TOKEN` on outbound attempt). Rejected because freezing is bidirectional (the lever meant for suspending a compromised participant) and reversible right up until `TokenFreezeTransaction` is actually called. **Correction to a previous entry here**: this file once stated as fact that a frozen account can't receive further transfers either. Never actually tested — inferred from freeze semantics, not measured. Moot now; treat as unverified if it resurfaces.

4. **Ephemeral keypair, used once for the required association, then discarded — built, then rejected on principle.** `hedera/create-discarded-key-retirement-account.mjs` (account `0.0.10422087`, kept as a superseded prototype). Worked mechanically: key signed exactly one `TokenAssociateTransaction`, then was never stored, written, or printed; outbound attempt with no signature failed with `INVALID_SIGNATURE`. Rejected anyway: "we discarded it" is a claim about a private process on one laptop, unverifiable by anyone else — exactly the kind of trust assumption this project exists to remove. Do not resurrect this approach; it was a mistake in judgment, not a technical failure, so it needs a decision override, not a retest, to come back.

**Adopted: deterministic, published key.**
```
seed = sha256("QUOTA-RETIREMENT-" + tokenId)   // tokenId = "0.0.10411251" for this token
key  = PrivateKey.fromBytesED25519(seed)
```
`hedera/create-deterministic-retirement-account.mjs`. Retirement account `0.0.10422283`. Verified, not just asserted, on two axes:
- **The account really uses the derived key** — on-chain confirmation via mirror node: registered key `fd2149afe5e06e4ac09bf505e772cdab662d768ab257170af7454d73c5ede5f2` matches the raw public key from the derivation exactly.
- **The key really is spendable, not just theoretically** — the script itself moves 1 gram out (signed with the reproduced key: `SUCCESS`) and back in (`SUCCESS`), demonstrating the residual risk concretely rather than asserting it.

25,000 grams retired into it. Attacker capability: anyone reproducing the two-line derivation can sign a transfer out, same as we just did. Detection: any such transfer is a public, permanent Hedera transaction against one specific known account that legitimate flows never draw from; today that means the mirror node, and once Layer 2's subgraph exists, a direct queryable anomaly. Same "prevention where we can, detection where we can't" framing as Trust boundaries below — this is a second instance of it, not a one-off.

No private key is stored in `.env` for this account — there's nothing to protect; it's re-derivable on demand from the token ID by anyone, including future sessions.

**Structural finding, confirmed and general, not an incident to be filed away:** `setMaxAutomaticTokenAssociations` cannot bootstrap an account into holding a KYC-gated token. Auto-association only takes effect as a side effect of a *successful* transfer; a transfer to a not-yet-KYC'd account fails first (`ACCOUNT_KYC_NOT_GRANTED_FOR_TOKEN`), and KYC can never be granted before an association exists (`TOKEN_NOT_ASSOCIATED_TO_ACCOUNT`). For any token with a `kycKey` — including future consortium tokens, not just this one — there is no way to get an account holding it without that account signing an explicit `TokenAssociateTransaction` at least once. This constraint shapes every future script that creates an account meant to hold QUOTA units. Found via an account (`0.0.10422047`) permanently stranded by a first attempt that assumed auto-association would work — unassociated, key already discarded, unrecoverable.

Each consortium-season gets its own retirement account under this scheme (the derivation includes the token ID, so a new season's token deterministically produces a different, independently reproducible account) — retired totals are then one mirror-node query away per season, no indexing needed.

### Trust boundaries

State this plainly in the README, don't overclaim trustlessness:

- **ENS is the policy layer**: cap, yield ratios, season window, minter roles.
- **QuotaAnchor (Sepolia) is the authorization record**: a mint is only legitimate if it has a matching ENS-authorized anchor event.
- **The relayer is bound to ENS state** and refuses to mint otherwise — demonstrated three ways under Status, not just described here: mints when authorized, refuses without touching the contract when the role is revoked, and refuses again once the season expires, isolating each check from the other.
- **The off-chain reconciler is the actual detector; the subgraph makes its findings queryable.** Precise phrasing matters here, corrected from an earlier looser draft: subgraph mappings can't call the Hedera mirror node (deterministic, no outbound HTTP), so the subgraph itself never "reconciles" anything. `scripts/relayer.mjs reconcile-mints` fetches full Hedera mint history and full Sepolia anchor history, and anchors `UnauthorizedMintDetected` for any mismatch; the subgraph just indexes that event. See "Bridging Hedera mirror-node data into the subgraph" below for the full design and the two bugs found building it.
- Explicit limitation: the Hedera `supplyKey` holder *could* mint without going through the relayer/ENS check — Hedera consensus has no knowledge of ENS or Sepolia, so that mint would still succeed on Hedera. It would, however, surface as an `UnauthorizedMintDetected` entity once the reconciler next runs and the subgraph indexes it. We can't make unauthorized minting impossible; we make it impossible to hide.
- Same framing for retirement-account outflows, with two mechanisms that are **not equivalent coverage** — don't let them read as interchangeable in any doc:
  - **The off-chain reconciler is the actual detector**, same as for mints. `checkRetirementTripwire` in `scripts/relayer.mjs` is that reconciler for the retirement side, anchoring `RetirementOutflowDetected`; the subgraph indexes it.
  - **That reconciler is opportunistic, not continuous.** Compares current balance to anchored total, only at the moment the relayer happens to run for some unrelated reason. No schedule, no continuous watch. An outflow immediately followed by a covering inflow before the relayer's next invocation would pass through unflagged specifically by that run — a later run, or the mint-reconciler's equivalent per-transaction approach if extended to retirements, would still catch it from full history.

### Bridging Hedera mirror-node data into the subgraph

**The constraint:** subgraph mapping handlers are deterministic, sandboxed WASM. They react only to events on the indexed chain and cannot make outbound HTTP calls to an arbitrary REST API. There is no way for a subgraph mapping to reach the Hedera mirror node directly — this is foundational to how The Graph guarantees reproducible indexing, not a missing feature.

**The design:** reconciliation happens off-chain, in `scripts/relayer.mjs`, extending the exact pattern already built for the retirement tripwire:
1. Fetch the full Hedera mint transaction history for the token from the mirror node (`reconcileMints()`).
2. Fetch the full `UnitsMinted` anchor-event history from `QuotaAnchor` — from **every address this project has ever deployed the contract to**, not just the current one (see gotcha below for why this matters).
3. Anchor `UnauthorizedMintDetected(seasonId, grams, hederaTxId)` for any Hedera mint with no matching anchor anywhere.
4. The subgraph indexes that event into an `UnauthorizedMint` entity. It never talks to Hedera; it only ever sees what the reconciler chose to anchor.

**Two real bugs, found by running it, not by inspection:**
1. First run checked only the current `QuotaAnchor` address's `UnitsMinted` history. Every mint legitimately anchored against a now-superseded address (this project redeployed several times for real reasons — closing the ENS TODO, adding the detector event, fixing a missing `seasonId` on `SeasonOpened`) came back as a false "unauthorized." Not a flaw in the detector logic — checking the wrong ground truth. Fixed by querying `ALL_ANCHOR_DEPLOYMENTS`, every deployed address, merged. This is the *correct* design regardless of how many times a contract gets redeployed; a stable production deployment wouldn't need the list to be long, but the reconciler still needs to be built to check it.
2. Second run, after that fix, *still* produced false positives. `normalizeHederaTxId` used chained non-global `.replace("@","-").replace(".","-")` — `String.replace` with a string argument only replaces the first match, and the account portion `0.0.x` already contains dots, so the second `.replace()` hit the wrong dot and neither ID format (SDK's `0.0.x@seconds.nanos`, mirror node's `0.0.x-seconds-nanos`) ended up canonicalized consistently. Same class of bug as the HashScan URL fix earlier in this project — chained single-character-string replace on a string with repeated separator characters. Fixed with an explicit regex (`/^(\d+\.\d+\.\d+)[@-](\d+)[.-](\d+)$/`) that parses both formats unambiguously; verified independently (`normalize(sdkFormat) === normalize(mirrorFormat)`) before rerunning.

**Verified clean, after both fixes:** minted 1 gram legitimately through the relayer (anchored on the current contract), then minted 1 gram directly via Hedera SDK bypassing the relayer entirely (`scripts/mint-bypassing-relayer.mjs` — kept as a permanent testing tool, not deleted after use) to simulate a genuinely unauthorized mint. `reconcile-mints` flagged exactly the bypass mint and correctly recognized every legitimately-anchored mint, including ones anchored against three different historical contract addresses. This is also where a timestamp cutoff (`ANCHOR_SYSTEM_START_SECONDS = 1788870000`) was added: mints from before `QuotaAnchor` existed (the original invariant-proof testing, done via raw Hedera scripts in Layer 1's earliest work) are out of scope for the detector — "unanchored" is their correct, expected state, not a finding, the same situation as the 25,000-gram retirement backlog documented above.

The two buggy runs did write real, immutable `UnauthorizedMintDetected` false positives on two now-deprecated contract addresses before the fixes landed — can't be undone, so those addresses were abandoned (redeployed past) rather than left for the subgraph to index. See Status for the full deployment history.

**A third bug, found later, from a different cause: ABI drift across a signature-changing redeploy.** v7 added `lotRef` to `UnitsMinted`, which changes the event's topic0 (keccak256 of its signature). Querying a pre-v7 deployment with v7's ABI silently returns *zero* logs for it — not an error, just a topic that never matches anything actually emitted there, because the deployed bytecode emits the old 4-field event, not the new 5-field one. Every mint anchored on v1–v6 would look "unmatched" again, the same symptom as bug #1 but from a completely different cause. Fixed by giving `ALL_ANCHOR_DEPLOYMENTS` a per-entry ABI fragment (`OLD_UNITS_MINTED_ABI` for v1–v6, `NEW_UNITS_MINTED_ABI` for the current one) so each deployment is queried with the event shape it actually emits. The general lesson: a redeploy that changes an event's *signature* (not just adds a new event) breaks history-spanning queries in a way that fails silently, not loudly — worth checking explicitly any time an indexed event's parameter list changes.

### Enforcing the yield ceiling on-chain, not just computing it

**Before v7:** `recordTransform` took a caller-supplied `yieldBp` and trusted it — the contract did the floor-division arithmetic correctly, but nothing stopped the relayer (or anyone who could call it) from passing a `yieldBp` higher than what ENS actually declares. The ratio was *displayed* correctly; it was never *enforced*.

**v7:** `recordTransform` reads `quota.yield.<productType>.bp` live from the input season's own ENS resolver on every call, computes the ceiling itself, and takes a caller-claimed `outputGrams` instead of a caller-claimed ratio — reverting `"QuotaAnchor: output exceeds yield ceiling"` if the claim exceeds what ENS permits. This mirrors `openSeason`'s existing pattern (read the number that matters from ENS, don't trust whoever's calling) applied to the one place that pattern hadn't reached yet.

**Proven, not just asserted:** against the real 2026 season (`quota.yield.kernel.bp = "4500"`), transforming 1000g of harvest input:
```
Claim outputGrams = 500 (ceiling is 450): reverts "QuotaAnchor: output exceeds yield ceiling", no Hedera token touched
Claim outputGrams = 450 (exactly the ceiling): succeeds
```
The relayer's `transform` command runs the ceiling check *first*, before any real Hedera transfer or mint — a bad claim fails cleanly with nothing to unwind, rather than requiring a real value movement to be reversed after the fact.

**Input consumption is retirement, not burning**, consistent with Layer 1's core design: the relayer transfers `inputGrams` from a dedicated processor account to the harvest token's existing retirement account (real `TransferTransaction`, anchored as `recordRetirement`) rather than calling anything resembling a burn. The processor account uses the same deterministic-key scheme as the retirement account (`sha256("QUOTA-PROCESSOR-" + tokenId)`, published, no stored secret) — it needs to *sign* an outbound transfer (retirement accounts never do), so it needs a reproducible key, not just a receiving address.

**The output product needs its own token, season, and retirement account** — genuinely new infrastructure, not reused: `hedera/create-kernel-token.mjs` creates a second FINITE-supply HTS token (`maxSupply` = the harvest cap at the declared yield ratio, `1,530,000,000` grams), `hedera/create-kernel-retirement-account.mjs` creates its retirement account via the identical deterministic formula keyed on the new token's ID (the "a new season's token produces a different, independently reproducible account" property, now actually exercised for a second time), and `kernel-2026.bronte.quota.eth` is registered under `bronte.quota.eth` exactly like the harvest season was, with its own `quota.cap.g` text record and its own `openSeason` call on `QuotaAnchor`.

**Registering `kernel-2026` surfaced the same role-bootstrap gap the harvest season's registration had already solved once.** `register-subname.mjs`'s `extraRoleBitmap` parameter exists specifically to grant the registrant `MINTER_ROLE_ADMIN` on the new resource at registration time — omitted, the registrant holds *zero* roles on that resource (not even by virtue of ERC1155 ownership; `ownerOf`/`hasRoles`/`hasRootRoles` were checked directly to confirm this, not assumed) and `grantRoles` reverts for anyone, including the owner. First `kernel-2026` registration omitted it; fixed by calling `unregister` (permitted — the deployer holds the parent-level `REGISTRAR` role that gates `register`/`unregister`, a different resource than the child's own role bitmap) and re-registering with `extraRoleBitmap = MINTER_ROLE_ADMIN`. Confirms the bootstrap mechanism has to be used every time a new resource needs role management, not just once.

**One real end-to-end lot, run for real, closing the loop:** `mint 1000g (lot-2026-003)` → `transfer 1000g` (operator → processor) → `transform` (rejected at 500g, accepted at 450g = exactly 4500bp of 1000g) → input 1000g retired (processor → harvest retirement account) → output 450g minted (kernel token) → `retire-kernel 450g` (operator → kernel retirement account). Every step a real Hedera transaction anchored with its real tx ID; grams conserved and independently checkable at every boundary. See Status and the dashboard's Chain view.

### Three-level ENS permission structure (Consortium / Control Body / Issuer)

**Renamed from "Approver" to "Control Body."** "Approver" was vague — it said what the role could do, not who it is. The real-world term is *organismo di controllo* (an accredited, independent control body): in the EU geographical-indication system, an independent control body verifies that a producer's harvest is genuine. It certifies; it does not own the denomination (that's the Consortium) and must never be able to issue units (that's the Issuer). Renamed throughout the Demo tab, README, and this file. **Internal identifiers were deliberately left alone** — `ENS_APPROVER_ADDRESS`/`ENS_APPROVER_KEY` in `.env`, `ens/generate-keypair.mjs ENS_APPROVER`, `config.approverAddress` in `app/server`'s `/config` response, and every `approver*`-prefixed variable in `scripts/relayer.mjs` and `app/server/index.mjs` still say "approver." Renaming those touches code and a live server response shape for zero user-visible benefit (nobody but this codebase ever reads `approverAddress`), so they were left as an internal-naming choice, not a mismatch to fix — every place a human actually reads the word, it now says "Control Body." The ENS subname *was* renamed (`control-body.bronte.quota.eth`, replacing `approver.bronte.quota.eth`) since that one *is* human-facing, and the swap cost about five minutes with zero risk to the actual `MINTER_ROLE_ADMIN` grant (which lives on the season resource, entirely independent of this display-only subname) — see below.

**No contract change.** `QuotaAnchor.recordMint`/`recordTransform` only ever do a read-only `hasRoles(tokenId, MINTER_ROLE, certifier)` check — never grant or revoke anything — and `hasRoles` is a per-account bitmap, so multiple `MINTER` holders already worked before this. Splitting "certifier" into three levels is entirely an ENS-side reconfiguration:

- **Consortium** — owns `bronte.quota.eth`, holds the parent registry's `REGISTRAR` role. Unchanged. Real-world identity: the Consorzio del Pistacchio Verde di Bronte DOP -- owns the denomination, does not certify producers.
- **Control Body** — holds `MINTER_ROLE_ADMIN` (`MINTER_ROLE << 128`, bit 168) and NOT `MINTER`. Can grant and revoke `MINTER` on other addresses; cannot mint. A dedicated, freshly-derived keypair (`ens/generate-keypair.mjs ENS_APPROVER` → `ENS_APPROVER_ADDRESS`/`ENS_APPROVER_KEY` in `.env`) — never the relayer's `SEPOLIA_DEPLOYER_KEY`. Conflating the infrastructure signer with the Control Body would undermine the separation this exists to prove.
- **Issuer** — two addresses hold `MINTER`: `ENS_CERTIFIER_ADDRESS` (Issuer 1, unchanged address, extended terminology) and a newly generated `ENS_ISSUER_2_ADDRESS`. Neither holds a private key that's ever used — same as the original certifier, an issuer is only ever checked via `hasRoles`, never asked to sign. Either can mint; neither can grant or revoke. Real-world identity: a certified producer.

**Getting `MINTER_ROLE_ADMIN` onto a genuinely new address needed more than a `grantRoles` call — confirmed empirically, not assumed, before building anything on top of an assumption:**
```
relayer (already holding MINTER_ROLE_ADMIN on the resource) calls
  grantRoles(tokenId, MINTER_ROLE_ADMIN, newAddress):        REVERTED
relayer calls grantRootRoles(MINTER_ROLE_ADMIN, newAddress): REVERTED
relayer's own root-level roles bitmap:                       REGISTRAR, REGISTRAR_ADMIN,
                                                               SET_SUBREGISTRY(+ADMIN),
                                                               SET_RESOLVER(+ADMIN), RENEW,
                                                               UNREGISTER — no MINTER-related bit
```
Root cause, structural not incidental: `EnhancedAccessControl`'s generic "admin of role R is `R << 128`" scheme has no valid admin bit for a role already in the top half of the 256-bit space. `MINTER_ROLE_ADMIN` is bit 168; its own "admin of admin" would be `168 + 128 = 296`, which overflows a `uint256` and is simply discarded by `SHL` (becomes `0`). So no per-resource `grantRoles` call can ever move an ADMIN-tier bit to a new address, and the relayer's root roles (granted once, at `ens/deploy-registry.mjs` time) never included blanket coverage of QUOTA's custom bits anyway. **The only place an ADMIN-tier bit can be assigned at all is `register()`'s `extraRoleBitmap` parameter, and it grants to exactly one address: the new owner.** This is the same constraint that produced the `kernel-2026` role-bootstrap fix earlier in this project (see "Enforcing the yield ceiling on-chain" above) — that fix generalizes exactly this far: it's not just "the registrant needs `extraRoleBitmap`," it's "an ADMIN-tier bit can only ever enter a resource via registration, never via a later grant, no matter who's asking."

**Fix: `ens/rotate-season-admin.mjs`**, a small reusable script — unregister the season (relayer's root `UNREGISTER` role authorizes this, a separate authority from anything held on the resource itself), then re-register with `owner = newAddress`, `extraRoleBitmap = MINTER_ROLE_ADMIN`, same resolver, same label, expiry extended. Resolver and node (namehash) are unchanged by this, so every text record already set (`quota.cap.g`, `quota.yield.kernel.bp`, etc.) survives untouched — confirmed by reading them back after rotation, not assumed. Run once against `2026.bronte.quota.eth`: new tokenId `...011919` (was `...011918`), new expiry `2026-12-09T14:30:32Z`.

**Confirmed on-chain, all four quadrants, after rotation:**
```
approver: hasAdmin=true  hasMinter=false
relayer:  hasAdmin=false hasMinter=false   (its ADMIN grant was on the OLD, now-superseded tokenId)
issuer1:  hasAdmin=false hasMinter=false   (until re-granted, below — its old grant was on the OLD tokenId too)
issuer2:  hasAdmin=false hasMinter=false
```
**The relayer still holds `MINTER_ROLE_ADMIN` as a leftover from the original season registration** — on the old, now-orphaned resource id. `findTokenId(label)` (what every live check, including `QuotaAnchor`'s, actually resolves) always returns the current id, so this is inert, not a live privilege. Left as-is rather than cleaned up further; noted here rather than silently fixed, per the project's own pattern of documenting a correction instead of editing history away.

**The Control Body then granted `MINTER` to both issuers, signed with its own key** (`ens/grant-minter.mjs`, generalized to take an explicit `signerPrivateKey` parameter instead of hardcoding the relayer's — defaults to `ENS_APPROVER_KEY` on the CLI). Real transactions, not simulated: grant issuer1, grant issuer2, then revoke+re-grant issuer2 as a round-trip proof of genuine revoke authority. A freshly generated keypair holds no ETH, so the Control Body needed a small Sepolia ETH funding transfer from the relayer (0.02 ETH, worthless testnet currency) before it could sign anything — the same category of infrastructure top-up as `ensureProcessorHbar`, just for a different gas token.

**Proof that admin authority does not imply minting authority**, the whole point of the split: `checkSeasonAuthorization("2026", approverAddress)` — off-chain courtesy check, no transaction sent —
```
REFUSED: 0x2006deb6e0E8ed48E2B2AfAf463Ae3E480B9E375 does not hold MINTER role
for "2026". No transaction sent.
```
— and a real end-to-end 1-gram mint by issuer1 (lot `lot-2026-approver-rotation-proof`) confirmed the whole pipeline still works post-rotation. Reproduced again in the Demo tab's Control Body section (see below) with a live "Attempt mint as Control Body" button, same refusal message, same guarantee.

**Display names, presentation only — the role checks never consult them.** `control-body.bronte.quota.eth`, `issuer-1.bronte.quota.eth`, `issuer-2.bronte.quota.eth` registered under `bronte.quota.eth` (`ens/register-subname.mjs`, `owner` = the role's own address, `extraRoleBitmap = 0`, non-transferable — same pattern as `rossi.bronte.quota.eth`), each with its resolver `addr()` record set to the matching address (`ens/set-addr-record.mjs`, new — confirmed the deployer holds `SET_ADDR` as a ROOT role on the shared resolver, granted once at `ens/register-root.mjs` deploy time, before assuming it could write; read every record back after setting it, all three matched). `control-body.bronte.quota.eth` supersedes `approver.bronte.quota.eth` (unregistered in the same session the role itself was renamed -- see "Three-level ENS permission structure" above for why that swap was worth doing rather than just patching the display label). The Demo tab (`labels.ts`'s `KNOWN_ROLE_NAMES`/`roleName()`) shows the name as primary text with the address as secondary, everywhere a Control Body/Issuer address is displayed — same "we know it because we registered it, there's no reverse-record lookup" reasoning as `KNOWN_SEASON_NAMES`/`KNOWN_CONSORTIA`. `QuotaAnchor` and every `hasRoles` check still operate on raw addresses only; nothing about authorization reads from ENS names or these addr records. Tree-shaken out of the production bundle along with the rest of `DemoView.tsx` — confirmed by grepping `dist/assets/*.js` for the three names, zero matches, same discipline as every other Demo-tab check in this file.

## Design requirements

- Full asset lifecycle: issuance, compliance-controlled transfer, transformation, retirement — with KYC/freeze controls, a custom fee schedule, and (planned) HCS mirroring alongside HTS.
- One shared subgraph schema indexing multiple consortia through a single query pattern, backed by a real Subgraph Studio deployment (project slug: `quota`) — no mocked data. Live at `https://api.studio.thegraph.com/query/1758548/quota/v0.0.2`, synced to chain head, all three example queries run against it for real (see Status).
- ENS must be central to authorization, not decorative. Kill test: delete ENS state and the system stops functioning — no mint authorization, no season boundaries, no cap values, no participant identity. Proven, not just designed for: see Layer 3 and Status.

## Architecture — three layers

**Layer 1 — the asset, Hedera testnet, `@hashgraph/sdk` only.**
One HTS fungible token per consortium-season.
- `supplyType: FINITE`, `maxSupply` = certified harvest in grams (e.g. `3_400_000_000`)
- `decimals: 3` — display only; dividing raw grams by 1000 happens to render as kg on explorers
- `supplyKey` — mints at harvest; the only key retained (see below)
- **No `adminKey`, no `wipeKey`, no `pauseKey`** — fully immutable token, no way to change terms after creation
- Custom fixed fee (consortium levy) set **at creation time**, no `feeScheduleKey` — the fee is immutable too, since without an admin key there's no way to add a fee-schedule key later
- `kycKey` — gates which supply-chain participants may hold units
- `freezeKey` — suspends a compromised participant. Not used for retirement (see Making retirement permanent) — retirement uses a deterministic, published key instead, so freeze stays dedicated to its real purpose
- The cap is enforced by Hedera consensus, not our code. Do not reimplement it in Solidity.

**Layer 2 — public accountability, Ethereum Sepolia.**
`QuotaAnchor.sol` — deployed and verified: v7, [`0x13A0Bb73C5a629dF1a8c91F99213d6077cc1acE2`](https://sepolia.etherscan.io/address/0x13A0Bb73C5a629dF1a8c91F99213d6077cc1acE2#code) (Etherscan, Blockscout, and Sourcify all verified -- see Known gotchas for why Etherscan's run looked stuck the first two times it was tried) (`QUOTA_ANCHOR_ADDRESS` in `.env`, current -- the only address the subgraph and every live link in README point at; see Status below for the full deployment history and why six earlier addresses are deprecated, two of them holding immutable false-positive detector events that must never be linked as if current). Stores almost nothing: the immutable `relayer` address (`onlyRelayer` modifier, set once at construction, never rotatable — without this anyone could emit fabricated anchor events for Hedera transaction IDs that never happened), plus one small struct per season (`seasonEns` mapping: parent registry, label, resolver, node) recording where to look on ENS, set once at `openSeason` and read — never re-supplied by the caller — on every later `recordMint`/`recordTransform`. Everything else is emit-only. Events:
```
SeasonOpened(seasonId, consortiumId, year, capGrams, hederaTokenId, ensNode)
UnitsMinted(seasonId, to, grams, hederaTxId, lotRef)
UnitsTransferred(seasonId, from, to, grams)
Transformed(inputSeasonId, inputGrams, outputSeasonId, outputGrams, productType, yieldBp, lotRef)
UnitsRetired(seasonId, grams, lotRef, hederaTxId)
ParticipantRegistered(consortiumId, addr, role)
RetirementOutflowDetected(seasonId, grams, hederaTxId)   // anchored by the relayer's opportunistic tripwire
UnauthorizedMintDetected(seasonId, grams, hederaTxId)    // anchored by the off-chain mint reconciler -- the actual detector
```
`openSeason`'s `capGrams` is read live from the resolver (`quota.cap.g`, parsed as a plain decimal string -- no float parsing) at anchor time, not caller-supplied. Confirmed by decoding the actual `SeasonOpened` event after running it, not just by the code reading correctly: `capGrams = 3400000000`.

`recordMint` takes a `certifier` address and checks two things on-chain, in that order, independently of whatever the relayer already checked off-chain: (1) `IEnsRegistry(parentRegistry).getResolver(label) != address(0)` -- does the season currently resolve; (2) `hasRoles(tokenId, MINTER_ROLE, certifier)` -- does the certifier hold the role. Kept as two separate checks even though both turn out to be expiry-gated (see Layer 3 below for the corrected finding) -- checking resolution explicitly keeps the contract's intent legible rather than depending on an indirect side effect of role resolution. `lotRef` is assigned here too, at mint time -- a lot's identity starts at harvest, not at retirement.

`recordTransform` (v7, redesigned -- see "Transformation, made real" below) no longer takes a caller-supplied `yieldBp`. It reads the input season's own ENS text record (`quota.yield.<productType>.bp`) live, computes `maxOutputGrams = inputGrams * yieldBp / 10000` (floored), and reverts `"QuotaAnchor: output exceeds yield ceiling"` if the caller-claimed `outputGrams` exceeds it. `yieldBp` in the emitted event is always what the contract itself just read and enforced, never a value someone passed in.

A small synchronous relayer (`scripts/relayer.mjs`) performs the HTS operation, then writes the anchor event. Keep it dumb: no queue, no retries. If the Hedera leg succeeds and the anchor leg fails, it logs loudly and exits non-zero rather than swallowing the mismatch. Before every `mint`, it also runs its own off-chain courtesy check (`checkSeasonAuthorization`) mirroring the contract's two checks -- if either fails, it refuses without sending any transaction at all, which is what "no contract was touched" actually looks like in proof (b) under Status. Implemented today: `open-season`, `open-kernel-season`, `mint`, `transfer`, `transform`, `retire`, `retire-kernel`, `register-participant`, `reconcile-mints`. `transform` orders its own steps for safety: it calls `recordTransform` (the ceiling check) on Sepolia *first*, before touching any real Hedera balance -- a bad claim reverts cleanly with nothing to unwind. Only after that succeeds does it run the real Hedera legs (input retired to the retirement account, output minted on the kernel token) and anchor both.

**Layer 3 — ENS v2 on Sepolia, load-bearing, not decoration. Live on Sepolia testnet, not aspirational.**
```
quota.eth                              0xbdc85dd5...4f2c4f0e2's ETHRegistrar, paid in MockDAI
 └── bronte.quota.eth                  consortium, owns its own subregistry
     ├── 2026.bronte.quota.eth         harvest season, real expiry (see Status for the value used and why)
     ├── kernel-2026.bronte.quota.eth  derived-product (kernel) season, same expiry scheme, own cap
     └── rossi.bronte.quota.eth        participant, registered with no ROLE_CAN_TRANSFER_ADMIN
```
Addresses in `.env`: `ENS_QUOTA_REGISTRY_ADDRESS` (quota.eth's own subregistry), `ENS_RESOLVER_ADDRESS` (one shared instance -- `text()` takes `node` as a parameter, so one resolver instance serves every node in the tree), `ENS_BRONTE_REGISTRY_ADDRESS` (bronte's own subregistry, holds every season and participant name), `ENS_SEASON_TOKEN_ID` / `ENS_KERNEL_SEASON_TOKEN_ID` (each season's own EAC resource -- these are two *different* resources, roles granted on one say nothing about the other; `ENS_SEASON_TOKEN_ID` shifts whenever the season is re-registered, e.g. the Control Body rotation below, so treat it as a cached convenience, always re-derived live via `findTokenId` in any code path that matters), `ENS_CERTIFIER_ADDRESS` (Issuer 1 -- a generated test address, never used to sign anything; QuotaAnchor only ever checks whether it holds a role, so it needs no private key at all), `ENS_ISSUER_2_ADDRESS` (Issuer 2, same no-key pattern), `ENS_APPROVER_ADDRESS` / `ENS_APPROVER_KEY` (the Control Body -- unlike the issuers, this one genuinely signs `grantRoles`/`revokeRoles` transactions, so it's the one role-address in this project that actually needs a private key; env var names kept as "approver" for continuity, see "Three-level ENS permission structure" below for why).

Four load-bearing mechanisms, each confirmed against verified on-chain source, not assumed from docs:
1. **Season subname expiry is the mint window** — `getResolver(label)`/`getSubregistry(label)` (string-label lookups) are expiry-gated directly (return the zero address once expired). `hasRoles(tokenId, role, account)` is *also* expiry-gated, but indirectly: `_constructResource()` computes the resource as `eacVersionId` normally, `eacVersionId + 1` once expired -- a version nothing has ever been granted a role on, so every role check returns `false` post-expiry without any stored role data being touched. (First read of the source concluded `hasRoles` wasn't expiry-gated at all -- wrong, from reading `getResource` but not `_constructResource` underneath it. Proof (c) under Status caught the contradiction empirically -- `hasRoles` returned `false` when the original claim said it should still be `true` -- and that's what triggered rereading the source properly. Left the wrong claim's correction visible in README rather than quietly fixing it, since the catch is as informative as the fact.) QuotaAnchor's resolution check (`getResolver != 0`) is the entire mint window regardless, with no timer and no `closeSeason()` anywhere in this codebase -- the authority to mint simply stops existing once real wall-clock time passes the expiry stored on ENS, checked passively on read, not by any scheduled job.
2. **EAC grants a MINTER role scoped to the season name.** Custom bit, not part of ENSv2's own `RegistryRolesLib` — `MINTER_ROLE = 1 << 40` (nybble 10, confirmed unused by reading the verified `RegistryRolesLib.sol` source before picking it, not guessed). Must match exactly between `ens/roles.mjs`, `scripts/relayer.mjs`, and the contract's `MINTER_ROLE` constant — there's no single source of truth for this value across three languages/files, which is a real maintenance risk worth fixing if this project continues (see Open decisions).
3. **Resolver text records are the canonical parameters**, set and read back from the resolver directly (not just trusted from the write): `quota.unit = "g"`, `quota.cap.g = "3400000000"`, `quota.token.hedera = "0.0.10411251"`, `quota.yield.kernel.bp = "4500"`, `quota.yield.cream.bp = "4000"`. QuotaAnchor reads `quota.cap.g` on-chain via a small decimal-string parser (`_parseUint`) -- basis points and grams, never decimal strings with a `.` in them, no float parsing anywhere in the whole stack.
4. **Participant subnames are non-transferable**, confirmed against source: `PermissionedRegistry._update()` (the ERC1155 transfer hook) reverts with `TransferDisallowed` unless the current owner holds `ROLE_CAN_TRANSFER_ADMIN` on their own token. `rossi.bronte.quota.eth` was registered with roleBitmap `0` -- no special code, just omitting one bit, and the registry itself makes the name unsellable.

**Registration mechanics, found empirically, not from docs:**
- Registration on this ENSv2 Sepolia beta pays in a mock ERC20 (`MockDAI`, `0x5472c5725a00b7ba11f0794a79d08ade6f4683bd`), not ETH. `getRegisterPrice(label, duration, address(0))` reverts with `PaymentTokenNotSupported(address)` -- confirmed by decoding the actual error selector against the rent price oracle's ABI, not guessed. `MockDAI.mint(address,uint256)` is public (it's an explicit testnet faucet token). Flow: mint, approve, `commit()`, wait `MIN_COMMITMENT_AGE` (60s), `register()`.
- Registering a name under `.eth` requires supplying a subregistry and resolver address at registration time, which means deploying your own `PermissionedRegistry`/`PermissionedResolverImpl` proxy instances (via `VerifiableFactory.deployProxy`) *before* the registration call, not after.
- All ABIs and role-bit constants used throughout `ens/` were pulled from Etherscan's `getabi`/`getsourcecode` API against the live, verified Sepolia contracts (see `ens/abi/*.abi.json`), not from ens-contracts GitHub source or documentation, to guarantee an exact match with what's actually deployed on this beta.

**The subgraph — one shared schema, Ethereum Sepolia, Subgraph Studio slug `quota`.**
`subgraph/schema.graphql`: `Consortium`, `Season`, `Participant`, `Lot`, `Mint`, `Transfer`, `Transformation`, `Retirement`, plus two detector entities (`UnauthorizedMint`, `UnauthorizedRetirementOutflow`) — all consortium-scoped by construction. `Season`'s `mintedGrams`/`retiredGrams`/`inCirculationGrams`/`utilisationBp` are computed in `subgraph/src/mapping.ts` on every relevant event (`recomputeSeasonAggregates`), not left to query-time aggregation.

`Lot` identity is `(seasonId, lotRef)`, assigned at mint time (not retirement) since v7. A `Transformation` links two *different* `Lot` entities — `inputLot` (input season, same lotRef) and `outputLot` (output season, same lotRef string) — since a lot's identity crosses from the input product's season into the output product's season at the moment it's transformed; the same lotRef string names two different Lot entities, one per season, and `Transformation` is the join between them. `Mint`, `Retirement` each link to exactly one `Lot`.

`Transfer` is indexed (`UnitsTransferred`, not indexed before v7) but is *not* lot-attributed — the contract's `recordTransfer` never gained a `lotRef` parameter, deliberately, so a `Transfer` links only to its `Season`. The dashboard's Chain view shows a season's transfers alongside a lot's journey by season and time, labeled explicitly as season-level, rather than implying an attribution precision the underlying event doesn't have.

Scaffolded by hand (`graph-cli`/`graph-ts` installed directly, manifest/schema/mappings hand-written) rather than `graph init`, to avoid its interactive prompts in a non-interactive environment — same reasoning as avoiding `hardhat --init` earlier. `graph codegen` and `graph build` both succeed against the current (v7) contract. One real gotcha hit immediately: this graph-cli version requires an explicit `@entity(immutable: true|false)` on every entity — `@entity` alone fails codegen outright (`@entity directive requires 'immutable' argument`), not documented anywhere obvious, found from the actual error message.

`ParticipantRegistered` was found missing `consortiumId` (address+role only) while writing the schema — without it, `Participant` couldn't be scoped to a consortium, breaking the composability claim specifically for participants. Fixed before the schema was written against it, in the same redeploy cycle as the detector event, not as a separate round.

The mint-reconciliation detector and its three real bugs are covered in full under "Bridging Hedera mirror-node data into the subgraph" above.

**Layer 4 — the dashboard, `app/`.** Vite + React + TypeScript + Tailwind v4, deploys to Vercel, reads directly from the live subgraph endpoint and directly from Sepolia via a public RPC (`ethereum-sepolia-rpc.publicnode.com` — no backend, no API key, since anything in a client bundle is public by definition). Three views: **Solvency** (per-consortium, per-season cap/minted/retired/in-circulation, with detector findings shown inline, not behind a tab), **Chain** (a lot's real journey — mint through transfer, transformation, and retirement, grams shown at every step), **Season** (ENS name, expiry, text records, and current `MINTER` role holders, all read live, not cached and not from the subgraph). Grams are the only unit carried internally; conversion to kg happens once, at the render edge (`lib/format.ts`), never earlier. Current `MINTER` holders aren't directly enumerable from `hasRoles` (it only answers "does this one account hold it"), so the app reconstructs a candidate set from every `EACRolesChanged` event the registry has emitted, then confirms current status for each with a live `hasRoles` call — deliberately not reimplementing the registry's own expiry/version-shift logic client-side (see "Making retirement permanent" for why that logic is subtler than it looks).

### Known gotchas
- `Client.forTestnet()` keeps the Node process alive unless `.close()` is called explicitly.
- Hardhat 3 requires ESM (`"type": "module"`) and a `hardhat.config.ts` using `defineConfig` — a `.js`/`.mjs` config fails with `HHE3`.
- The public Sepolia RPC (`ethereum-sepolia-rpc.publicnode.com`) caps `eth_getLogs` at a 50,000-block range. Querying event history from block 0 fails outright (`exceed maximum block range: 50000`) once the chain is taller than that — always pass `fromBlock` starting at `QUOTA_ANCHOR_DEPLOY_BLOCK`, never 0.
- HashScan transaction URLs are `https://hashscan.io/testnet/transaction/{account-id}-{seconds}-{nanos}` — keep the dots in the account ID, only replace `@` and the timestamp's internal `.` with `-`. Verified against a real transaction page; an earlier guess (dashing every character) produced "Invalid transaction id".
- `gh` CLI is broken on this machine (wrong CPU architecture); git operations go over SSH with a dedicated key, not HTTPS/gh.
- Without an `adminKey`, the token's `kycKey`/`freezeKey`/fee schedule can never be changed after creation — deliberate (immutability is the point), but any mistake in those parameters at creation time is permanent for this token.
- Hedera validates account-key satisfiability everywhere a key can be set, not just at creation: an empty `KeyList` fails with `KEY_REQUIRED`, a `KeyList` whose threshold exceeds its member count fails with `INVALID_ADMIN_KEY` — on `AccountCreateTransaction` and on `AccountUpdateTransaction` alike. Settled: there is no way to construct a genuinely unspendable account on Hedera. Don't re-investigate this.
- `TokenGrantKycTransaction` requires the target account to already be associated with the token (`TOKEN_NOT_ASSOCIATED_TO_ACCOUNT` otherwise), and `TokenAssociateTransaction` always requires the account's own signature — no exception, even with `setMaxAutomaticTokenAssociations` set. Auto-association only fires as a side effect of a *successful* transfer, and a transfer to a not-yet-KYC'd account fails first (`ACCOUNT_KYC_NOT_GRANTED_FOR_TOKEN`), so for a KYC-gated token there's no way to bootstrap an account into holding it without signing an explicit association at least once. Applies to every account this project ever creates to hold QUOTA units, not just retirement accounts.
- `TokenFreezeTransaction` blocks transfers in *both* directions, not just outbound — noted for the record from the now-superseded freeze-based retirement prototype; not verified by us directly and not relevant to the current retirement mechanism.
- "We generated a key and discarded it" is not an acceptable design for anything user-facing in this project, even though it works mechanically — it reintroduces exactly the kind of unverifiable trust claim the product exists to remove. Prefer deterministic/published or otherwise independently verifiable constructions.
- ENSv2 Sepolia beta registration pays in `MockDAI`, not ETH — `getRegisterPrice(..., address(0))` reverts `PaymentTokenNotSupported`. `MockDAI.mint()` is public.
- `.eth` registration requires a subregistry and resolver address *at* the `register()` call — deploy your own `VerifiableFactory.deployProxy` instances first, not after.
- `PermissionedRegistry.getResolver(label)`/`getSubregistry(label)` (string-label lookups) are expiry-gated directly (return zero once expired). `hasRoles(tokenId, role, account)` is expiry-gated too, but indirectly: `_constructResource()` shifts to `eacVersionId + 1` once expired, a resource nothing was ever granted a role on. Both mechanisms agree at expiry; QuotaAnchor still checks both separately for legibility, not because only one is expiry-aware.
- `PermissionedRegistry._update()` reverts `TransferDisallowed` unless the current owner holds `ROLE_CAN_TRANSFER_ADMIN` on their own token — the mechanism behind non-transferable participant subnames, confirmed in source rather than assumed.
- `MINTER_ROLE = 1 << 40` must be kept in sync by hand across `ens/roles.mjs`, `scripts/relayer.mjs`, and `QuotaAnchor.sol`'s constant — no single source of truth for this value. A drift here fails silently as "certifier lacks role" rather than a clear error.
- graph-cli 0.98.1 requires an explicit `@entity(immutable: true|false)` on every schema entity — plain `@entity` fails codegen with `@entity directive requires 'immutable' argument`, not obviously documented, found from the actual error.
- A subgraph reconciler comparing off-chain history (Hedera mirror node, or any external source) against on-chain anchors must check **every address the anchor contract has ever been deployed to**, not just the current one, if the contract has ever been redeployed — checking only the current address produces false positives for everything legitimately anchored pre-redeploy. Found the hard way, fixed generally (`ALL_ANCHOR_DEPLOYMENTS` in `scripts/relayer.mjs`), not just patched for this one case.
- Chained non-global `String.replace(a, b).replace(c, d)` on a string with repeated separator characters (e.g. `"0.0.x@seconds.nanos"`, which has dots in both the account portion and the timestamp) silently normalizes wrong — only the first match of each replace gets hit. Bit twice in this project (HashScan URL construction earlier, `normalizeHederaTxId` here). Use an explicit regex or split-based parse whenever a string's structure has repeated separators, not chained single replaces.
- Redeploying a contract with a *changed event signature* (not just a new event) silently breaks any history-spanning query that reuses the old ABI against the new address, or vice versa — the event's topic0 changes, so a filter built from the wrong ABI matches nothing on that specific deployment rather than erroring. `scripts/relayer.mjs`'s `ALL_ANCHOR_DEPLOYMENTS` now carries a per-entry ABI fragment for exactly this reason (v7 added `lotRef` to `UnitsMinted`).
- `PermissionedRegistry.register()`'s `extraRoleBitmap` argument is the *only* way the registrant gets any role (including `*_ADMIN` bits like `MINTER_ROLE_ADMIN`) on a newly-registered resource — ERC1155 ownership (`ownerOf`) grants no implicit role access, confirmed directly (`hasRoles`/`hasRootRoles` both return `false` for the owner when `extraRoleBitmap` was omitted). Omit it and `grantRoles` reverts for everyone, including the owner, with no bootstrap path except `unregister` + re-register with the bit included.
- An ADMIN-tier EAC role bit (anything already in the top half of the 256-bit space, i.e. any `X << 128`) can **never** be assigned to a new address via an ordinary `grantRoles`/`grantRootRoles` call, no matter who holds what -- `EnhancedAccessControl`'s "admin of role R is `R << 128`" scheme produces an admin bit beyond 255 for any such R, which `SHL` simply discards to `0`. The *only* place an ADMIN-tier bit can ever be assigned is `register()`'s `extraRoleBitmap`, and only to the one address being registered as owner. Confirmed empirically (a `grantRoles(tokenId, MINTER_ROLE_ADMIN, newAddress)` staticCall from the current holder reverts) before building the three-level permission structure on top of an assumption. Generalizes the `kernel-2026` role-bootstrap fix from earlier in this project into a hard rule, not a one-off.
- **Corrected entry** (this file previously stated, wrongly, that Etherscan verification was "stuck behind their V1→V2 API migration"): checked directly against the API and it was never true. `@nomicfoundation/hardhat-verify` 3.1.0 already targets `api.etherscan.io/v2/api` (confirmed by reading the installed package's source, not assumed), and a raw `curl` to that endpoint with the project's API key returned in under half a second. What actually happened: `hardhat verify` tries a minimal compiler input first, and if Etherscan can't verify against that, retries with the full solc input used to actually compile and deploy -- a second full submit-and-poll cycle. Two earlier attempts this session were killed (`TaskStop`) after a few minutes of "Waiting for verification result..." with no visible progress, mistaking normal two-phase latency for a hang. Left to run to completion, it printed the retry message and verified successfully. Lesson: for anything that submits-then-polls with no intermediate output, prefer letting it finish (or checking the target's API directly, as done here) over killing it on a guess. This entry stays as a correction, not a silent fix, since the earlier wrong claim already reached README.md and CLAUDE.md before being caught.
